# scripts/ 的 CI 端功能現況

從根目錄 `CLAUDE.md` 搬來的完整現況與限制；根目錄只留摘要與安全禁令。

**AI 修復 PR（已接入並啟用，修復路徑待首次實跑驗收）**：CI 在 E2E 失敗後由 AI 開修復 PR 並回報結果。**已完成**：伺服器端 `POST /api/ai-fix`（契約見 `docs/api.md` §8；經 HMAC，依心跳名稱找 `test_failure` issue，存入 `issues.ai_fix_*` 四欄，`pr_opened` 且 PR 為新時在告警討論串通知負責人）、issue 詳情頁顯示 AI 修復結果、判讀腳本 `scripts/diagnose-e2e-failure.sh` 的 `needsCodeChange` 輸出與 `DIAGNOSE_REDACTED_OUT`、CI 端修復腳本 `scripts/ai-fix-e2e-failure.sh`（去重、agent 呼叫、越界檢查、commit／PR、回報）、onboarding skill 的「執行時 checkout」與「AI 修復 PR」接入段。**腳本分發**：各 CI repo 不複製腳本，而是在 workflow 執行時 checkout th-beacon 的釘選 commit（deploy key，`ref` 為 workflow 內的 40 碼 SHA 字面值）；改腳本後 push th-beacon，再人工更新各 repo workflow 內的 `ref`。**停用開關**：App repo 的 `ai-fix` job 以 repo variable `AI_FIX_ENABLED == 'true'` 為啟用條件（variable 不存在＝預設關閉，由使用者驗收時開啟；緊急停用改掉或刪除它即可，伺服器端不需回滾）；job 失敗時尾端 step 以 `AI_FIX_REPORT_ONLY=failed` 補報 `failed`。**現況（2026-11-17）**：Trustnel 兩個 repo（Android／iOS）的 workflow 已接入並 push，釘選 th-beacon `129ffd4`；兩邊各手動觸發一次 E2E 皆成功，確認「執行時 checkout（deploy key＋SHA＋sparse-checkout）」、建置不受 `.beacon/` 干擾、心跳回報正常；兩個 repo 的 `AI_FIX_ENABLED` 已設為 `true`。**尚未驗證**：E2E 失敗後的整條路（判讀 → `ai-fix` job → agent 權限旗標 → GitHub App 推分支開 PR → `/api/ai-fix` 回報與 Discord 通知）至今沒有在 CI 上實跑過，第一次真實失敗即第一次實測；Anthropic federation rule 只允許 `refs/heads/main`，故無法在測試分支驗收（除非另建臨時 rule）。Spec：`docs/superpowers/specs/2026-11-13-ai-fix-pr-design.md`；Plan：`docs/superpowers/plans/2026-11-13-ai-fix-pr.md`。

**資安監控（已實作，待首次實跑驗收）**：每日由 GitHub Actions 掃描各服務並在 dashboard 的 `/security` 頁面顯示，七項檢查（ports／updates／logins／cert／logVolume／exposure／changes），不發 Discord、不進 issue 管線。**已完成**：`src/core/security/` 純函式（payload 驗證、log 量／暴露／變動判定、憑證狀態、整體狀態與過期、檢視模型）；`POST /api/security-scan`（HMAC，契約見 `docs/api.md` §9，body 上限 512 KB）與 `security_scans` 表（線上 migration 已套用，保留 90 天）；runner 端 CLI `scripts/security/scan.mts`＋`lib/*.ts`（Node 直接執行 `.mts`，故 `src/core/security/**` 只用相對路徑加 `.ts` 副檔名 import）與 VM 上執行的 `scripts/security/collect-vm.sh`；`ai_usage.source` 新增 `ci_security`。**分工**：排程端只送事實與 Claude 對 ports／updates／logins 的判讀（Claude 不帶任何工具、輸入不含原始登入紀錄），logVolume／exposure／changes 由 beacon 寫入時算、cert 與過期在讀取端推導。**Workflow**：`.github/workflows/security-scan.yml`（本 repo 第一個 workflow，只允許 schedule／workflow_dispatch，持有 GCP 與各服務 HMAC 憑證，勿加 `pull_request`／`push` 觸發）；目標清單 `security/targets.json` **目前為空陣列（待使用者填入）**，空清單時 scan job 會被跳過。**尚未驗證**：收集腳本從未在真實 Ubuntu 上執行過（只在 macOS 以假指令驗證）、workflow 從未實跑（IAP／OS Login／IAM 角色／Anthropic 聯邦規則皆為假設）、`/security` 頁面沒有人目視驗證過；驗收清單在 spec §11。**啟用前必做**：workflow 已依目標種類分 `security-vm`／`security-hosted` 兩個 environment，但 GCP workload identity 的 attribute condition 須由使用者設為只信任 `security-vm`（見 spec §11）。**已知限制**：**快照與 ingest 共用同一把服務金鑰**——這把金鑰也存在於被監控的服務自身，取得它的人可以推送偽造的「全部正常」快照（`scannedAt` 的 2 小時下限只擋回填舊基準，擋不住偽造當下的快照；根本解法是掃描器改用只存在於 GitHub secrets 的獨立金鑰，本版未做，啟用前最該知道這一條）；掃描器連線帳號等同該 VM 的 root（遠端指令形如 `sudo … bash`，無法以 sudoers 限縮）；收集腳本是變動偵測而非完整入侵偵測（容器清單比對映像檔來源但不含版本），防火牆判定不處理 deny 規則，hosted 稽核只支援 pnpm／npm，log 量來源支援 file／journal／docker（docker 型只算現存容器，部署後與 json-file 輪替會使數字偏低），hosted 稽核已淨化 `package.json` 並釘版 pnpm、workflow 的第三方 action 已釘 commit SHA（細節見 spec 的「已知限制」）。Spec：`docs/superpowers/specs/2026-11-18-security-monitoring-design.md`；Plan：`docs/superpowers/plans/2026-11-18-security-monitoring.md`。
